# 실험 이력과 회고 (SafeCar 부하테스트 재검증, 2026-10-14 \~)

목적: 어떤 실험에서 **무엇을 고정하고 무엇을 바꿨는지**, 중간에 **무엇을 놓쳤고 어떻게 고쳤는지**를 쌓아 두고, 다음에 테스트할 때 **어떤 순서로 하면 좋은지**를 회고로 남긴다.
실험을 하나 끝낼 때마다 아래 1번 표에 한 줄, 2번에 놓친 점, 필요하면 3번 순서를 갱신한다.
상세 수치는 정리 문서(`부하테스트_재현.md`)의 해당 절을 본다. 이 문서는 요약판이라 일부 수치는 반올림했다.

## 0. 이번에 알게 된 큰 그림
- **튜닝은 병목인 자원을 건드릴 때만 효과가 보인다.** 에러율이 이미 0–2%로 낮은 구간(바닥 효과)에서는 설정 변경에 따른 에러율 개선을 구분하기 어려웠다. 부하를 올려 압박이 생긴 구간(8000명)에서야 기본값과 튜닝값의 차이가 보이기 시작했으나, accept를 맞추면 그 차이도 사라졌다(아래).
- 측정값을 흔드는 것은 설정보다 **측정 환경**(시간대, 창 상태, 절전, 도구의 표시 방식)인 경우가 많았다.
- **스레드·풀·accept를 분리해 보니(2x2x2) accept를 1000으로 맞춘 조건에서는 스레드·풀의 뚜렷한 차이가 관찰되지 않았다.** accept가 작을 때만 조합에 따라 에러가 크게 갈렸다(1.6% \~ 13.4%). accept를 키우면서 거절이 대기로 바뀌어 차이가 가려졌을 가능성이 있다. 다만 연결 거절은 줄었어도 p95가 더 길어지지는 않아 "대기로 바뀌었다"는 설명은 확인하지 못했다.
- **이 환경에서 가장 확실한 개선은 show-sql 끄기**였다(5회씩 반복, 범위 안 겹침: 켠 상태에서 끄면 처리량 약 30% 증가, p95 약 47% 감소). 가장 값싸고 분명한 효과는 복잡한 튜닝이 아니라 불필요한 로그를 끄는 것이었다.
- 같은 부하를 만드는 JMeter가 같은 CPU를 써서(한 노트북), 서버 성능과 부하 생성기 성능이 섞인다.

## 2. 중간에 놓쳤던 것과 고친 방법
| 놓친 것 | 어떻게 드러났나 | 고친 방법 / 다음에는 |
|---|---|---|
| 환경 안정성 확인 없이 설정부터 비교 | Phase 1 v1이 시간대에 따라 오염 | 같은 조건(기준선)을 먼저 반복해 안정한지 확인하고, 비교 때도 기준선을 섞어 넣는다 |
| 창 상태가 변수라는 것 | 2x2 실험 뒤에야 확인 | 장시간 측정은 처음부터 숨김 창 + 출력 리다이렉트. GUI 측정은 창 상태를 조건으로 기록 |
| 설정을 한꺼번에 바꾼 비교 (2월 M→N→O, 이번 기본값 vs 튜닝값) | 원인 분리 불가 | 한 번에 하나씩 또는 요인 설계(2x2x2) |
| 조건당 반복이 적음(1–3회) | 흔들림이 효과보다 큼 | 포화 부하에서 5회 이상, 조건 순서를 번갈아 |
| 압박이 없는 부하에서 비교 | 5000명은 에러 0–2%라 차이 안 보임 | 먼저 포화점(에러가 나기 시작하는 부하)을 찾고 그 부근에서 비교 |
| 병목 위치를 재지 않고 추정 | CPU 가설만 있었음 | 처음부터 프로세스별 CPU(앱, JMeter, DB, Docker)를 같이 기록 |
| 지연 분포(p95)를 안 잼 | 에러 외 지표 부족 | 에러, TPS, p95를 항상 같이 기록 |
| 공식의 W 정의 | 2월은 커넥션 획득 대기를 W로 썼음 | W는 "CPU를 쓰지 않고 기다리는 시간"(DB 응답 대기 등)으로 정의하고, DB를 분리한 환경에서 잰다 |
| 풀을 고정해 두고 Tomcat/Consumer를 나눔 | MQ 도입 시 시행착오로 값 결정 | 요청 경로 C/W 측정 → Tomcat 계산 → Consumer 산정 → 풀 크기 결정 순서 |
| 도구가 만든 오류 | Start 이중 클릭(샘플 10만 건), CSV 천 단위 쉼표, CPU 샘플러 첫 구현 오류(합 100% 초과, PostgreSQL 0) | 결과를 쓰기 전에 샘플 수·열 수·값 범위를 검증하고, 본 실험 전에 스모크 테스트 |
| 실행 환경 사고 | 파일 잠금으로 스크립트가 죽음(약 30분 손실), `run-case.ps1` BOM 제거, 절전으로 스크립트 정지, 원본 DB `safecar`에 시뮬레이터 5행 | 로그는 공유 읽기, 한글 경로 스크립트는 BOM, 장시간 스크립트는 절전 방지, 측정은 `safecar_retest`만 사용 |
| 포화점을 찾는 큐에서 시작 조건 미충족 시행이 섞임 | 1회차 앞 3개가 `calm=False` | 시행마다 `calm`을 기록해 두었으니 분석할 때 걸러낸다. 시작 조건을 못 채우면 쉬는 시간을 늘려 다시 한다 |
| 블록 순서의 영향(2회차 블록에 높은 에러가 몰림) | 2x2x2에서 2회차 때 `t200 a100`이 24–25%, `t7 p30 a100`이 13% | 조건 순서를 번갈아도 반복 블록 단위의 흔들림은 남는다. 블록마다 기준 조건(canary)을 하나씩 섞어 넣는다 |
| 조건당 3회로 요인 효과를 말함 | 같은 조건 범위(5–25%)가 효과(2–10%p)와 비슷 | 효과를 말하려면 5회 이상과 간단한 검정(예: 순열 검정) |
| 에러율만 보면 show-sql 켠 쪽이 좋아 보임 | 켠 쪽 중앙값 1.21% vs 끈 쪽 2.57% | 에러율, 성공 TPS, p95를 항상 같이 본다 |

## 3. 다음에 테스트한다면: 권장 순서
0. **환경과 도구 고정:** 전원 연결, 절전 방지, 숨김 창 + 출력 리다이렉트, 서비스(PostgreSQL, Docker) 확인, 가능하면 부하 생성기와 DB를 다른 PC로 분리. 측정 스크립트는 스모크 테스트로 먼저 검증(샘플 수, 열, 값 범위).
1. **기준선(canary)을 반복 측정:** 같은 조건을 여러 번 돌려 안정한지 확인. 시간대·열 영향을 보려면 비교 실험 중간중간에도 넣는다.
2. **포화점과 병목 찾기:** 부하를 단계적으로 올리며(1000 → 8000 이상) 에러, TPS, p95, 프로세스별 CPU를 기록. 에러가 나기 시작하는 부하를 비교 구간으로 정한다.
3. **C/W 측정과 계산:** 낮은 부하에서 서버 지표로 재고, W를 정의대로(DB 응답 대기) 구해 적정 스레드를 계산. 첫 값으로 돌려 다시 재고 수렴할 때까지 반복.
4. **한 번에 한 설정씩 비교:** 외부 요인(accept 등)은 같게 두고 스레드, 풀, accept를 요인별로 바꾼다(필요하면 2x2x2). 포화 부하에서 조건당 5회 이상, 조건 순서를 번갈아.
5. **확인과 반증:** 효과가 보이면 그 원인이 맞는지(예: accept가 에러를 대기로 바꾼 건 아닌지) 하나만 바꿔 다시 확인.
6. **즉시 기록:** 실험을 하나 끝낼 때마다 이 문서의 1번 표와 2번에 추가한다.
